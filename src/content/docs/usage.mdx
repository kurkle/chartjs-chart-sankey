Sankey data points define directed flows between named nodes.

```js
{
  from: 'Coal',
  to: 'Electricity',
  flow: 42
}
```

`hoverColorFrom` and `hoverColorTo` are never simply unset: leaving them out doesn't turn off the hover effect, it falls back to a computed color — `colorFrom`/`colorTo` run through Chart.js's own `getHoverColor` helper (saturated by 0.5, darkened by 0.1). To get no color change on hover, set `hoverColorFrom`/`hoverColorTo` explicitly to the same value as `colorFrom`/`colorTo`.

## Node Labels

Use `nodeLabels` to place and style labels globally or by node. Position names follow Chart.js layout positions, with `auto` preserving Sankey's automatic left/right placement.

```js
nodeLabels: {
  position: {
    Coal: 'right',
    Electricity: 'center',
    Energy: 'left'
  },
  color: (node) => node.key === 'Electricity' ? 'white' : 'black',
  backgroundColor: {
    Electricity: 'blue'
  },
  borderRadius: 3,
  padding: 4,
  font: {
    size: 11,
    weight: 'normal'
  }
}
```

## Node Padding

`nodePadding` sets the gap between nodes stacked in the same column, in CSS pixels. The layout is done in pixels once the chart area is known, so the gap is exact: the column that determines the scale (the one with the most to fit) renders exactly the requested gap, and other columns never get a smaller one. In `auto` mode a column with room to spare may show a larger gap where aligning a node with its flows asks for it. If the gaps alone would take more than half of the axis, every gap is shrunk by the same factor so that the flows stay visible. Like `nodeLabels`, it resolves per node, in three forms:

- A plain number applies the same gap everywhere: `nodePadding: 20`.
- A `{ before, after }` object sets an asymmetric gap: more space above the node than below it, or vice versa. `before` is the gap above the node and `after` is the gap below it, regardless of `orientation` (in a vertical chart, "above"/"below" become "left"/"right" visually, but `before`/`after` keep the same meaning). Either side left out falls back to `10`.
- A function receiving the node and returning either form, for full control: `nodePadding: (node) => node.key === 'Coal' ? { after: 28 } : 4`.

A top-level object is always a `Record` of node keys (like `nodeLabels`), never a `{ before, after }` gap directly — that shape would be ambiguous with a keyed `Record`. Write a function for a global asymmetric gap instead:

```js
// per-node gaps, keyed by node
nodePadding: {
  Coal: { after: 28 },
  Solar: 4
}

// a global asymmetric gap: more space below every node than above it
nodePadding: () => ({ before: 4, after: 8 })
```

Gaps collapse like CSS margins instead of summing: the space between two adjacent nodes in a column is `max(prevNode.after, nextNode.before)`, not their sum. A plain `nodePadding: 10` is therefore equivalent to every node using `{ before: 10, after: 10 }` — `max(10, 10)` is still `10`.

### Node Padding Mode

By default (`nodePaddingMode: 'auto'`), the column that sets the scale (the one that fills the axis) is placed first, from the start of the cross axis, and the other columns follow outwards from it: every node goes where its flows meet the nodes already placed, and the heaviest flow of a node is kept straight, the others bend. A node with nothing placed beside it, and any room that is left over, goes towards the start of the axis (the top of a horizontal chart, the left of a vertical one). Nodes never get closer than the gap, and two nodes in the same column can end up with different gaps between them. Setting `nodePaddingMode: 'even'` instead moves a column as one block with exactly the requested gap between each pair: regular gaps, but the nodes are not aligned individually with their flows, so those flows bend more to reach them. Note that `size: 'min'` can make a node's drawn bar smaller than the flows it carries, so flows can still overlap visually in either mode.

See the [Node Padding sample](/samples/node-padding/) for a single wide gap separating groups within a column, and for `auto` vs. `even` side by side.

## Node Min Size

`nodeMinSize` gives a node's drawn bar a minimum size in CSS pixels, so a node carrying a tiny flow next to a huge one doesn't disappear into a sub-pixel line. It resolves per node, in the same three forms as `nodePadding`: a plain number (`nodeMinSize: 6`), a `Record` keyed by node key, or a function receiving the node. Defaults to `0`, meaning no minimum.

Only the drawn bar is stretched — the underlying data isn't. When a node's natural size (in flow units, converted to pixels) is smaller than `nodeMinSize`, its bar grows to `nodeMinSize` symmetrically around the node's real position: half the growth extends above/left, half below/right. The node's label follows the same stretched rectangle. The flows attached to the node keep their exact proportional height and still connect at the same points they always did — stretching the bar doesn't move or resize any flow, so a bar that grew to be visible can still have flows that are their own hairline thickness inside it.

Space for the stretch is reserved during layout, so a stretched bar does not overlap a neighboring node — the gap between two stretched bars in the same column still respects the requested `nodePadding`, in both `auto` and `even` mode.

`nodeMinSize` makes the *node* visible, not the *flow*. A flow of 0.37 arriving at a 6px node bar is still a hairline inside that bar — if the flow itself needs to be visible, the data needs a minimum applied before charting (e.g. clamped upstream), and that's usually worth calling out in a label rather than silently distorting the chart.

See the [Node Min Size sample](/samples/node-min-size/) for a huge node next to several tiny ones, with and without a minimum.

## Circular Flows

A flow whose target is in the same column as its source or in an earlier one is a back flow, and so is a flow from a node to itself. A back flow is laid out together with the nodes, like a flow that skips columns: it gets a slot, the size of the flow, in its source column, in its target column and in every column between them, and it runs through them from right to left (a horizontal chart; from bottom to top when vertical). It leaves the source, turns beside the source column, runs through its slots, turns beside the target column and enters the target from behind. The slots are ordered and placed with the nodes, so a loop may run between nodes, not only around all of them. There are no options for this.

- Which flows are back flows is decided from the data, not from its order: the flows are taken from the largest to the smallest, and one that would close a cycle with the flows before it is a back flow. A flow from a node to itself is always one. Use `column` to pin nodes where you want them.
- The order within a column is chosen to keep flows from crossing. A turn of a back flow counts as a crossing with every band that meets a slot between the node and the slot of its flow, and with the turns that interleave with it, so loops end up next to their nodes where that removes crossings, and loops that nest come out nested.
- The slots of one back flow are placed to run level across the columns where the other flows allow it, and step across in the gap between two columns where they do not.
- A slot is part of the content of its column: it takes its thickness and a small gap off the cross axis, and the turns take room beside the columns, so the bands are drawn thinner than the axis alone would allow when the chart is short along the columns or has very many loops. When there is not enough room, the gaps, the radii of the turns and the least thickness of a band (1 pixel) shrink together. Every back flow is routed; none is left as a curve between the nodes. With very many loops the bands become hairlines.
- Labels positioned outside the first or last column (`left`/`right`, or `top`/`bottom` when vertical) are kept clear of the turns.

See the [Circular Flows sample](/samples/circular-flows/).

## Flow Labels

Flow labels use the same visual options and display the numeric flow value. Since flows are Chart.js elements, these options use the standard scriptable context.

```js
flowLabels: {
  display: (context) => context.raw.flow >= 10,
  position: 'center',
  color: 'black',
  backgroundColor: 'white',
  borderRadius: 3,
  padding: 4,
  font: {
    size: 11,
    weight: 'normal'
  }
}
```

## Layout and parsed data

Which flows run backwards, the column of every node, the order of the nodes within a column and the order of the flows at each node are decided from the data alone. In a cyclic chart the flows are visited from the largest to the smallest and the one that would close a cycle is the back flow, so the biggest flows keep running forwards and the order of the data only breaks ties. The order of the nodes within a column is chosen to keep flows from crossing: nodes are first listed as the data mentions them, then moved towards the average position of the nodes they are connected to and neighbours are swapped where that removes crossings, a few times forward and backward, and the order with the least crossing is kept. A crossing weighs the smaller of its two flows, so a thin flow crossing a thick one costs little and two thick flows crossing cost a lot. Among orders of the same weight the one with fewer crossings wins, so a flow of no weight (zero or tiny) is still kept from running through other flows when that costs nothing. `priority` fixes the relative order of the nodes it names. A flow that skips columns takes room in each column it passes, as a waypoint the size of the flow, so it runs between the nodes of those columns instead of over them; waypoints take part in the order and the alignment, and the gap between two of them is 2 pixels (or `nodePadding` if that is smaller). Because they take room, a chart with many skipping flows is drawn with a smaller scale. Sizes, gaps and positions are computed in pixels when the chart area is known, so the title, the legend and `layout.padding` are respected and the scales are not used for the layout.

`parsed.x` and `parsed.y` of a flow no longer hold positions in value units. On the column axis (`x` for horizontal charts, `y` for vertical ones) `parsed` holds the column of the source node and `parsed._custom` the column of the target; the other axis is `0`. The pixel geometry of a flow is available on the element (`x`, `y`, `x2`, `y2`, `width`, `height`).
